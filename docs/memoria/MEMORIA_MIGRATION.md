## Onde cada coisa fica

- **`C:\DEV\Supabase\`** — todas as migrations SQL do banco:
  - `supabase_migracao_vNNN.sql` (novas versões sempre são criadas AQUI);
  - `criar_tabela_supabase.sql` — DDL da tabela `public.pedidos`;
  - `migracao_status.sql` — checks de migração/estado do banco.
- **Repo `bapzx`** — NÃO versionar .sql de Supabase. Se um arquivo SQL novo
  for gerado, criá-lo direto em `C:\DEV\Supabase`.
- **`tools/migrar_pedidos.py`** — ficou NO repo: é script Python que roda
  junto do projeto (migração de `pedidos.json` → Supabase via código), não é
  SQL.

## Aplicação das migrations (fluxo do dono)

1. O SQL é criado/salvo em `C:\DEV\Supabase\supabase_migracao_vNNN.sql`.
2. O dono abre o arquivo e cola no **SQL Editor** do Supabase (console) para
   aplicar.
3. Se o SQL der erro no console, ele é CORRIGIDO no arquivo em
   `C:\DEV\Supabase\` e o dono roda o bloco inteiro DE NOVO — as migrations são
   idempotentes (`create table if not exists` + seeds `on conflict do nothing`),
   garantir isso é obrigatório ao revisar um script.
4. Mensagens no painel (ex.: aviso no `/admin/coins`) podem citar o nome do
   arquivo (ex.: `supabase_migracao_v123.sql`) — o arquivo está em
   `C:\DEV\Supabase`, não no repo.
5. Exemplo real: v123 falhou com 428C9 (`cannot insert non-DEFAULT value into
   column "id"`, identity `generated ALWAYS`). Corrigido trocando para
   `generated BY DEFAULT` + bloco `do $$` que converte identity ALWAYS já
   criado; re-rodar o arquivo atualizado basta (não precisa dropar tabela).
6. **v124 APLICADA em 23/09/2026** (dono confirmou no SQL Editor do Supabase):
   `supabase_migracao_v124.sql` — marketplace (config, listings, pagamentos,
   `profiles.vip_until`) + índices `ix_marketplace_listings_*`. A v2.10.1
   deixou de enviar `tipo_pvp` (coluna fica com default vazia); sem migration
   nova na v2.10.1.
